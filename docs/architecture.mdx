# Architecture Overview

Vibe Kanban is a full-stack application built with **Rust** (backend) and **React + TypeScript** (frontend). This document provides a comprehensive overview of the project architecture, including both **standalone/local deployment** and **SaaS/cloud deployment** modes.

## Deployment Modes

Vibe Kanban supports two deployment modes:

| Feature | Standalone (Local) | SaaS (Cloud) |
|---------|-------------------|---------------|
| **Backend** | `crates/server` | `crates/remote` |
| **Frontend** | `frontend/` | `remote-frontend/` |
| **Database** | SQLite | PostgreSQL |
| **Authentication** | GitHub OAuth (personal) | JWT + OAuth (organizations) |
| **Storage** | Local filesystem | S3/R2 compatible |
| **Multi-tenancy** | No | Yes (Organizations) |
| **Use Case** | Individual developers | Teams & Enterprises |

## Rust Crates

### server (Standalone Mode)

**Purpose**: Main API server for individual/local users

**Characteristics**:
- SQLite database (WAL mode, 120 second busy timeout)
- GitHub OAuth authentication (personal)
- Local file system storage
- Single-user / single-machine deployment

**Key Files**:
- `crates/server/src/main.rs` - Entry point, server initialization
- `crates/server/src/routes/` - API route handlers
  - `config.rs` - Configuration endpoints
  - `projects.rs` - Project CRUD
  - `tasks.rs` - Task management
  - `task_attempts.rs` - Task execution attempts (core execution logic)
  - `oauth.rs` - GitHub OAuth
  - `events.rs` - Server-sent events for real-time updates
  - `containers.rs` - Container/service management
  - `approvals.rs` - Approval workflows

### remote (SaaS/Cloud Mode)

**Purpose**: Multi-tenant API server for teams and enterprises

**Characteristics**:
- PostgreSQL database (instead of SQLite)
- JWT + OAuth authentication (supports organizations)
- S3/R2 compatible object storage
- GitHub App integration for repository access
- Email notifications
- AES-GCM encryption for sensitive data
- Multi-tenant with organization support

**Key Files**:
- `crates/remote/src/main.rs` - Entry point
- `crates/remote/src/app.rs` - Application state and middleware
- `crates/remote/src/routes/` - API route handlers
  - `organizations.rs` - Organization/workspace management
  - `oauth.rs` - OAuth + GitHub App integration
  - `projects.rs`, `tasks.rs`, `task_attempts.rs` - Core task management
  - `shared_tasks.rs` - Cross-organization task sharing
  - `repo.rs` - Repository management
- `crates/remote/src/db/` - PostgreSQL database layer
- `crates/remote/src/github_app/` - GitHub App integration
- `crates/remote/src/auth/` - JWT authentication
- `crates/remote/src/mail.rs` - Email notifications
- `crates/remote/src/r2.rs` - S3/R2 object storage

### db

**Purpose**: Shared SQLx database models and migrations

**Models** (`crates/db/src/models/`):
- `task.rs` - Task model with status (Todo, InProgress, InReview, Done, Cancelled)
- `project.rs` - Project grouping tasks
- `workspace.rs` - Execution workspace (git branch, container ref)
- `execution_process.rs` - Running agent processes
- `coding_agent_turn.rs` - Individual agent turns
- `session.rs` - Execution sessions
- `project_repo.rs` - Git repositories per project
- `workspace_repo.rs` - Repositories per workspace
- `merge.rs` - Merge operations
- `scratch.rs` - Scratch notes
- `tag.rs` - Task tags
- `image.rs` - Screenshots/images
- `execution_process_logs.rs` - Process output logs

**Note**: Migrations are located in:
- `crates/server/migrations/` - Standalone mode migrations
- `crates/remote/migrations/` - SaaS mode migrations (PostgreSQL)

### executors

**Purpose**: Abstractions and implementations for various AI coding agents

**Supported Agents**:

- OpenAI Codex

### services

**Purpose**: High-level business logic and orchestration

**Services**:

**Purpose**: Trait-based deployment abstraction for local vs cloud

**Deployment Trait** defines:

## Core Data Models

### Task

```rust
pub struct Task {
    pub id: i64,
    pub project_id: i64,
    pub title: String,
    pub description: Option<String>,
    pub status: TaskStatus,  // Todo, InProgress, InReview, Done, Cancelled
    pub parent_workspace_id: Option<i64>,  // For nested tasks
    pub shared_task_id: Option<String>,    // For shared/linked tasks
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

### Workspace

```rust
pub struct Workspace {
    pub id: i64,
    pub task_id: i64,
    pub container_ref: Option<String>,
    pub branch: String,
    pub agent_working_dir: String,
    pub setup_completed_at: Option<DateTime<Utc>>,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

**Note**: Each task execution happens in a git worktree (isolated branch).

### ExecutionProcess

```rust
pub struct ExecutionProcess {
    pub id: i64,
    pub session_id: i64,
    pub status: ExecutionProcessStatus,  // running, completed, failed, killed
    pub run_reason: RunReason,  // setupscript, cleanupscript, codingagent
    // ...
}
```

### Session

Groups execution processes for a task attempt. Links workspace to execution.

### CodingAgentTurn

Individual turns within an execution with logs, diffs, and repo state snapshots.

## Architectural Patterns

| Pattern | Description |
|---------|-------------|
| **Workspace/Worktree** | Each task execution happens in a git worktree (isolated branch) |
| **Session/Attempt** | Tasks can have multiple attempts, each with multiple processes |
| **Executor Abstraction** | Pluggable executor pattern for different AI agents |
| **Service Container** | Central service container pattern for dependency injection |
| **Event Streaming** | Server-sent events (SSE) for real-time updates |
| **Deployment Abstraction** | Trait-based deployment allowing local vs cloud backends |
| **Type Generation** | Rust types automatically generate TypeScript definitions via ts-rs |

## Database Patterns

### Standalone Mode (server)
- **SQLite with WAL mode** for concurrent access
- **120 second busy timeout** to handle locks
- **SQLx with compile-time query verification** (via `prepare-db` script)
- Migration-based schema management
- Models as active records with static query methods
- Data stored in `~/.local/share/vibe-kanban/`

### SaaS Mode (remote)
- **PostgreSQL** for multi-tenant data isolation
- **SQLx** with PostgreSQL queries
- Organization-based data separation
- Connection pooling for scalability
- Migrations in `crates/remote/migrations/`

## Authentication Comparison

| Aspect | Standalone | SaaS |
|--------|-----------|------|
| **Method** | GitHub OAuth (personal) | JWT + OAuth (organizations) |
| **Tokens** | Session-based | JWT bearer tokens |
| **Users** | Single user per instance | Multi-user organizations |
| **GitHub** | Personal access token | GitHub App integration |

## Storage Comparison

## Key Commands

### Standalone Mode Development

```bash
# Start frontend + backend (auto ports)
pnpm run dev

# Backend with cargo-watch
pnpm run backend:dev:watch

# Frontend dev server
pnpm run frontend:dev
```

### SaaS Mode Development

```bash
# Start remote API (requires .env.remote)
cd crates/remote
cargo run --bin remote

# Or via Docker Compose
docker compose --env-file .env.remote -f crates/remote/docker-compose.yml up --build

# Start remote-frontend with SaaS API
export VK_SHARED_API_BASE=http://localhost:8081
cd remote-frontend
pnpm run dev
```

### Shared Commands

```bash
# Type Generation
pnpm run generate-types      # Generate TS types from Rust

# Database
pnpm run prepare-db          # Prepare SQLx (offline mode) - Standalone
cd crates/remote && sqlx migrate run # SaaS PostgreSQL migrations

# Testing
cargo test --workspace       # Run Rust tests
pnpm run check              # Type check frontend + backend

# Build
pnpm run build:npx          # Build NPX package (standalone)
pnpm pack                   # (in npx-cli/) Pack NPX package
```
