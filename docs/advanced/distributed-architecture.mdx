## Overview

Vibe Kanban supports distributed deployment patterns that allow you to:

- **Scale horizontally** - Deploy agents across multiple machines
- **Improve resilience** - No single point of failure
- **Optimize resources** - Leverage specialized hardware per agent type
- **Enable collaboration** - Multiple developers with isolated agent environments

<Warning>
Distributed deployments add complexity. Start with a single-node deployment and scale out when needed.
</Warning>

## Task Distribution Models

When deploying across multiple cloud nodes, you need to decide how tasks are shared and distributed.

### Model A: Centralized Orchestrator

A central coordinator manages a global task pool and distributes work to available nodes.

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Cloud Environment                            │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │              Central Orchestrator (VK Server)                │   │
│  │  - PostgreSQL (task queue + state)                           │   │
│  │  - Redis (task distribution)                                 │   │
│  │  - Global task pool                                          │   │
│  └───────────────────────┬─────────────────────────────────────┘   │
│                           │                                          │
│        ┌──────────────────┼──────────────────┐                     │
│        │                  │                  │                     │
│        ▼                  ▼                  ▼                     │
│  ┌──────────┐      ┌──────────┐      ┌──────────┐                │
│  │  Node A  │      │  Node B  │      │  Node C  │                │
│  │          │      │          │      │          │                │
│  │ Projects:│      │ Projects:│      │ Projects:│                │
│  │ vk, web  │      │ mobile   │      │ infra    │                │
│  │          │      │          │      │          │                │
│  │ Pulls    │      │ Pulls    │      │ Pulls    │                │
│  │ related  │      │ related  │      │ related  │                │
│  │ tasks    │      │ tasks    │      │ tasks    │                │
│  └──────────┘      └──────────┘      └──────────┘                │
└─────────────────────────────────────────────────────────────────────┘
```

**Workflow:**
1. All tasks enter the global task pool (PostgreSQL + Redis Queue)
2. Each node polls periodically: `GET /api/tasks?project=my-project&agent=available`
3. Orchestrator assigns tasks to appropriate nodes based on tags/projects
4. Node reports completion: `POST /api/tasks/{id}/complete`

**Pros:**
- Global task visibility, can reassign failed tasks
- Supports task prioritization and load balancing
- Easy monitoring and debugging

**Cons:**
- Single point of failure (requires HA setup)
- Network dependency

**Implementation:**

```rust
// crates/server/src/routes/task_distribution.rs

pub async fn claim_tasks(
    State(pool): State<PgPool>,
    Json(request): Json<ClaimTasksRequest>,
) -> Result<Json<ApiResponse<Vec<Task>>>, ApiError> {
    let node_id = &request.node_id;
    let projects = &request.projects;

    // Claim tasks with row-level locking
    let tasks = sqlx::query_as!(
        Task,
        r#"
        SELECT * FROM tasks
        WHERE project_id = ANY($1)
          AND status = 'pending'
        LIMIT $2
        FOR UPDATE SKIP LOCKED
        "#,
        projects,
        request.batch_size as i64
    )
    .fetch_all(&pool)
    .await?;

    // Mark tasks as claimed
    for task in &tasks {
        sqlx::query!(
            "UPDATE tasks SET status = 'claimed', assigned_node = $2, claimed_at = NOW() WHERE id = $1",
            task.id,
            node_id
        )
        .execute(&pool)
        .await?;
    }

    Ok(Json(ApiResponse::success(tasks)))
}
```

**Workflow Example:**

```bash
# 1. Central Orchestrator creates a task
# POST /api/tasks
{
  "project_id": "vibe-kanban",
  "title": "Fix authentication bug in login flow",
  "description": "Users cannot log in with special characters in password",
  "priority": "high",
  "target_node": "node-a"  // Only specify which node, not which agent
}

# 2. Node A's Decision Center (Claude Code) receives the task
# Analyzes task type → "bug fix in authentication code"
# Decides → Use OpenCode with Claude model (good at debugging)

# 3. Node A routes to OpenCode worker
# OpenCode executes the task with appropriate model

# 4. Result reported back to Central Orchestrator
```

**Node Decision Logic (Claude Code):**

```rust
// crates/services/src/services/decision_center.rs

pub struct DecisionCenter {
    claude_code_client: ClaudeCodeClient,
    opencode_workers: HashMap<String, OpenCodeWorker>,
}

impl DecisionCenter {
    pub async fn process_task(&self, task: Task) -> Result<TaskResult> {
        // Step 1: Analyze task with Claude Code
        let analysis = self.claude_code_client
            .analyze(&task)
            .await?;

        // Step 2: Select appropriate worker based on analysis
        let worker = self.select_worker(&analysis)?;

        // Step 3: Execute task with selected worker
        let result = worker.execute(task, analysis.model).await?;

        Ok(result)
    }

    fn select_worker(&self, analysis: &TaskAnalysis) -> Result<&OpenCodeWorker> {
        match analysis.task_type {
            TaskType::CodeEdit => Ok(self.opencode_workers.get("kimi").unwrap()),
            TaskType::CodeReview => Ok(self.opencode_workers.get("deepseek").unwrap()),
            TaskType::Architecture => Ok(self.opencode_workers.get("gpt4").unwrap()),
            TaskType::Documentation => Ok(self.opencode_workers.get("qwen").unwrap()),
            TaskType::Debugging => Ok(self.opencode_workers.get("claude").unwrap()),
            _ => Ok(self.opencode_workers.get("default").unwrap()),
        }
    }
}
```

### Comparison: Task Distribution Models

| Aspect | Centralized | Decentralized | Hybrid with Decision Center |
|--------|-------------|---------------|----------------------------|
| **Complexity** | Medium | High | Medium |
| **SPOF** | Yes (coordinator) | No | No |
| **Task Reassignment** | Easy | Difficult | Easy |
| **Network Dependency** | High | Low | Medium |
| **Load Balancing** | Automatic | Manual | Automatic |
| **Agent Selection** | Central | Per-node | Per-node (intelligent) |
| **Best For** | Teams < 50 | Distributed teams | Most scenarios |

<Info>
**Recommendation:** Use the **Hybrid with Decision Center** model. Claude Code excels at orchestration while OpenCode provides flexible model selection, creating an optimal division of labor.
</Info>

## Agent Lifecycle: Per-Task vs Long-Running

<Warning>
**Critical Architecture Constraint:** Vibe Kanban's core design is **1 task = 1 worktree**. Each task has its own isolated worktree directory where the agent operates. **Neither Claude Code nor OpenCode support dynamic worktree switching at runtime.** The working directory is fixed when the agent process starts.
</Warning>

### The Worktree Constraint

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Vibe Kanban Architecture                         │
│                                                                     │
│  Task 1 ──> Worktree A (/vk/worktrees/task-1-branch/)               │
│              └──> Agent runs in Worktree A                          │
│                                                                     │
│  Task 2 ──> Worktree B (/vk/worktrees/task-2-branch/)               │
│              └──> Agent runs in Worktree B                          │
│                                                                     │
│  Task 3 ──> Worktree C (/vk/worktrees/task-3-branch/)               │
│              └──> Agent runs in Worktree C                          │
└─────────────────────────────────────────────────────────────────────┘

### Current Behavior: Per-Task Spawning

<Warning>
By default, Vibe Kanban spawns a new agent process for each task in its dedicated worktree. This has significant performance overhead.
</Warning>

```
Task 1 → Create Worktree A → spawn npx claude-code (cwd: Worktree A) → Exit
Task 2 → Create Worktree B → spawn npx claude-code (cwd: Worktree B) → Exit
Task 3 → Create Worktree C → spawn npx claude-code (cwd: Worktree C) → Exit
         ↑                        ↑
         ~2s worktree creation    ~5-10s agent startup
```

### The Long-Running Agent Challenge

### Recommended Approaches

<Info>
**Best Practice: 1 Task = 1 Toolbox** - This perfectly aligns with vibe-kanban's architecture and eliminates the worktree switching problem entirely.
</Info>

#### Approach 1: Per-Task Toolbox (Recommended)

```
┌─────────────────────────────────────────────────────────────────────┐
│  1 Task = 1 Worktree = 1 Toolbox                                   │
│                                                                     │
│  Task 1 ──> Worktree A (/vk/workspaces/task-1-branch/)              │
│              └──> Toolbox A created in Worktree A                     │
│                   └──> Agent runs with cwd: Worktree A                 │
│                                                                     │
│  Task 2 ──> Worktree B (/vk/workspaces/task-2-branch/)              │
│              └──> Toolbox B created in Worktree B                     │
│                   └──> Agent runs with cwd: Worktree B                 │
│                                                                     │
│  Task 3 (follow-up to Task 1)                                      │
│              └──> Reuse Toolbox A (session fork)                     │
│                   └──> Agent runs with cwd: Worktree A                 │
└─────────────────────────────────────────────────────────────────────┘
```

**Workflow:**

```bash
# 1. Task created → Worktree created
vk-cli create-task --project my-project --branch feature/login-fix

# 2. Toolbox created in worktree directory
toolbox create --container vk-task-abc123
toolbox enter vk-task-abc123

# 3. Agent starts in correct directory (no cd needed)
$ npx -y @anthropic-ai/claude-code "fix login bug"

# 4. Follow-up attempt reuses toolbox
vk-cli create-attempt --task abc123 --follow-up
# Enters existing toolbox, uses session fork (~0s overhead)
```

**Pros:**
- ✅ Perfect alignment with VK architecture
- ✅ Agent starts in correct directory
- ✅ Follow-up tasks have zero startup overhead
- ✅ Complete isolation between tasks
- ✅ Toolbox persists across task attempts

**Cons:**
- ⚠️ One toolbox per active task (memory usage)
- ⚠️ Toolbox cleanup required after task completion

#### Approach 2: Per-Task Spawning (Legacy)

```
Task 1 → Worktree A → spawn agent (cwd: Worktree A) → Execute → Exit
Task 2 → Worktree B → spawn agent (cwd: Worktree B) → Execute → Exit
```

**Pros:** Complete isolation, works with all agents
**Cons:** 5-10s startup overhead per task

<Info>
**Recommendation:** Use **Approach 1 (Per-Task Toolbox)** for all production deployments. It provides the best performance by leveraging session fork for follow-up tasks while maintaining proper worktree isolation.
</Info>
```

#### Approach 2: Session Fork for Same Worktree

For multiple tasks on the same worktree (e.g., follow-up tasks):

### Configuration

```toml
# config/agent-pool.toml
[pool]
enable = true
mode = "worktree_aware"  # Agents accept worktree path parameter

[pool.agents.claude_code]
min = 2
max = 5
idle_timeout = 300  # Terminate after 5min idle

[pool.routing]
# High-volume simple tasks → pool
complex_tasks = "dedicated"  # Spawn dedicated agent
simple_tasks = "pooled"      # Use agent pool
```

### Comparison: Approaches

| Aspect | Per-Task Only | Worktree-Aware Pool | Hybrid |
|--------|---------------|---------------------|--------|
| **Startup Time** | 5-10s | ~0ms | Varies |
| **Worktree Isolation** | Perfect | Good | Perfect |
| **Resource Efficiency** | Low | High | Medium |
| **Complexity** | Simple | Medium | High |
| **Best For** | Development | High-volume simple tasks | Production mixed workload |

<Info>
**Recommendation:** Use **worktree-aware agent pool** for high-volume simple tasks (code edits, fixes). Use **dedicated agents** for complex, long-running tasks that benefit from full worktree isolation.
</Info>

## Claude Code + OpenCode Collaboration Pattern

This section details the recommended collaboration pattern between Claude Code and OpenCode on each node.

### Role Division

| Component | Role | Strengths |
|-----------|------|-----------|
| **Claude Code** | Decision Center & Orchestrator | Multi-agent coordination, task decomposition, complex workflows |
| **OpenCode** | Execution Worker | Easy model switching, multiple LLM providers, focused code tasks |

### Why This Combination Works

**Claude Code as Orchestrator:**
- Strong built-in support for coordinating multiple tools and agents
- Can break down complex tasks into subtasks
- Good at understanding context and dependencies
- Handles retries and error recovery gracefully

**OpenCode as Worker:**
- Supports 20+ LLM providers (Kimi, DeepSeek, GPT-4, Qwen, Claude, etc.)
- Easy model switching via configuration
- Optimized for code-focused tasks
- Lightweight and fast for individual operations

### API Flow

```rust
// crates/services/src/services/decision_center/flow.rs

pub async fn process_incoming_task(task: Task) -> Result<TaskResult> {
    // Step 1: Claude Code analyzes the task
    let plan = claude_code_client
        .create_execution_plan(&task)
        .await?;

    // Step 2: Execute subtasks through OpenCode workers
    let mut results = Vec::new();
    for subtask in plan.subtasks {
        let worker = opencode_pool
            .get_worker(&subtask.recommended_model)?;

        let result = worker
            .execute(subtask)
            .await?;

        results.push(result);
    }

    // Step 3: Claude Code aggregates results
    let final_result = claude_code_client
        .aggregate_results(results)
        .await?;

    // Step 4: Report to central orchestrator
    central_client
        .report_completion(task.id, final_result)
        .await?;

    Ok(final_result)
}
```

### Database Strategy

|-----------|---------|-------------|

### Distributed Transaction Pattern

```rust
use tokio::sync::RwLock;

struct DistributedTaskManager {
    local_db: PgPool,
    redis: RedisClient,
}

impl DistributedTaskManager {
    async fn create_task(&self, task: Task) -> Result<()> {
        // Begin transaction
        let mut tx = self.local_db.begin().await?;

        // Insert into local DB
        task.insert(&mut *tx).await?;

        // Publish to task queue
        self.redis
            .publish(&format!("tasks:{}", task.id), &task.to_json())
            .await?;

        // Commit
        tx.commit().await?;
        Ok(())
    }
}
```
